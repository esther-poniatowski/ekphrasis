# Custom checkers

A custom checker implements in Python a rule beyond the predefined checkers, as the [requirement on custom checkers](../requirements.md#^custom-checkers) demands. A project can thereby reuse the Python functions that already check its records, such as a check that every symbol of a formula is declared.

## Registration

A custom checker is a Python function registered under a name in the settings of the plugin. The settings declare three elements for all custom checkers:

- the absolute path to the Python executable used by the project;
- the maximum duration of one call, in milliseconds;
- the checker modules, each given by a file path in the vault or by an importable module name, together with the name under which each function is registered.

A schema invokes a registered checker by its name, under the key `check` of a [rule declaration](validation.md). Only registered functions can run, so a schema received from another source cannot execute code of its own choice.

A registration can also name the schemas whose instances its checker checks as a whole, without any rule declared by those schemas. Such an *instance checker* serves a project whose schemas are generated by its own tool and declare no rule of the plugin. Two optional elements of the registration select it:

- *Instance schemas*: glob patterns matched against the reference that binds the instance, such as `project:*`. The reference is the logical identifier of the field `_schema`, or the schema path of a path rule or a modeline.
- *Arguments*: a JSON object whose keys are passed to each call, since no rule declaration carries them.

An instance checker runs once per validation of a matching instance, after the rules declared by the schema. Its issues display at their own fields, as located issues below specify.

## Function contract

Each checker function receives the checked value and its context, and returns a list of issues and non-issue context items. The function below reports each symbol of a signature left undeclared by the variables of the record:

```python
def declared_symbols(value, *, instance, path, file, **arguments):
    """Report each symbol of the signature not declared by any variable of the record."""
    declared = {variable["symbol"] for variable in instance.get("variables") or []}
    return [f"Undeclared symbol: {symbol}" for symbol in value if symbol not in declared]
```

The parameters carry the following content:

| Parameter | Content |
| --- | --- |
| `value` | Value of the field that declares the rule, as parsed from YAML; the whole instance for an instance checker |
| `instance` | Whole instance, as parsed from YAML |
| `path` | [Field path](field-paths.md) of the field that declares the rule; empty for an instance checker |
| `file` | Absolute path of the instance, so that the checker can read neighbouring files |
| `arguments` | Further keys of the rule declaration, or the arguments of the registration of an instance checker |

A returned item takes one of three forms. A string is reported as an issue at the field that declares the rule, or at the root for an instance checker. A mapping with the keys `message` and `severity` is a *located issue*, reported at its own place, which one of three keys gives:

- `path`: a field path starting from the root of the instance, parsed with the syntax of [field paths](field-paths.md); a malformed field path reports an issue at the field that declared the checker;
- `pointer`: a JSON Pointer (RFC 6901) starting from the root of the instance, as a findings log writes its locus;
- `locus`: a location of another form, such as a typed locus `term:<id>`, which designates no field.

A located issue may also hold the key `discriminator`: a string naming the offending content, such as a symbol or a term, derived from that issue alone. When a domain tool runs the same function from its own command, the tool writes the key as the discriminator of its finding, in the [findings profile](https://github.com/esther-poniatowski/elenchos/blob/main/docs/profile.md) of the gate Elenchos. Therefore, two issues of one checker at one path keep distinct identities in the gate. With a pointer, the discriminator also completes the location. A producer may stop the pointer at a list whose entries are keyed by an identifier, and open the discriminator with the identifier of the entry, followed by the segments below it and the offending content, each part joined by `/`. The plugin then enters the one item of the list that holds the identifier as the value of one of its keys. Each later part remains in the field path while it names a field declared by the schema or a node of the instance, including when the offending content has the name of another declared field. The first other part is offending content. Where no single item holds the identifier, the issue stays at the list instead of selecting an arbitrary item. A typed locus designates no field of the current form, so its issue stays in the root report. ^pointer-location

A located issue may hold the key `controlled_by`, whose value is a JSON Pointer to the field whose authored value or presence activates the issue. When the pointer designates an existing non-root field, the validation summary groups the issue under that controlling field. Both the controlling field and the issue target remain links to their controls. A malformed pointer, the document root or a pointer that designates no form field leaves the issue ungrouped. This relation is supplied by the checker; Ekphrasis does not infer it from a rule name or a project-specific path.

A located issue may finally hold the keys `rule`, `result_class`, `repair_condition`, `documentation_target` and `source_file`, each a string. The form displays the rule, the result class, the repair condition and the documentation target below the message, as the tool wrote them, and keeps every key with the issue. An issue whose place designates no field of the form displays in the summary at the top of the form, with its location as the tool wrote it; the plugin moves no issue to a neighbouring field. An error located at a field left unfilled is reported as a missing field, and any other error as an invalid value, as for the [built-in checks](validation.md#issues). An exception raised by the function is reported as one issue at the declaring field, with the message of the exception.

A mapping with `kind` equal to `context` and string fields `label` and `value` states context for the current checker run. It may also hold string fields `description`, `result_class` and `documentation_target`. The form displays every supplied context below the schema binding and above the findings. Context remains outside the issue list, so it changes neither issue counts nor issue marks. The checker owns the meaning of each context; Ekphrasis does not derive a clean-result claim from an empty issue list.

## Tools publishing a findings log

A tool whose checks write a [SARIF](https://docs.oasis-open.org/sarif/sarif/v2.1.0/sarif-v2.1.0.html) 2.1.0 log needs no Python function written for the plugin. The runner provides the module `ekphrasis_findings`, whose function `findings_log` runs a command of the configured interpreter and returns the results of its log that concern the checked file. A registration names that module and that function, and can pass these arguments:

| Argument | Content |
| --- | --- |
| `command` | Arguments given to the interpreter, such as `["-m", "tool", "check", "{folder}", "--format", "sarif"]`; `{file}` and `{folder}` stand for the checked file and its folder |
| `root` | Working directory of the command, against which a relative artifact URI of the log resolves; `{folder}` by default |
| `context_property` | Optional name of a SARIF run property whose object, or list of objects, supplies checker context |

The command writes its log on standard output; its exit status is ignored when the log is readable. Each result whose artifact resolves to the checked file becomes a located issue: its message, its level (`error`, any other level becoming a warning), its rule, the locus that follows `#` in its logical location, and the discriminator `discriminator/v1` of its partial fingerprints. The properties `resultClass`, `repairCondition`, `documentationTarget` and `controllingDecision` of a result, prefixed by the name of the driver or not, give the result class, the repair condition, the documentation target and the controlling field. A run declared unsuccessful adds a warning at the root per notification, and a command that writes no readable log is reported at the root with the end of its error output.

For example, a project checked by Gnomon registers the checker below. Its interpreter is the one of the environment where Gnomon is installed:

```json
{
  "name": "gnomon",
  "module": "ekphrasis_findings",
  "function": "findings_log",
  "schemas": ["gnomon:*"],
  "arguments": {
    "command": ["-m", "gnomon", "check", "{folder}", "--scope", "question-typed", "--format", "sarif"],
    "context_property": "gnomon/validationScope"
  }
}
```

A check of one inquiry folder by Gnomon took about 8 seconds on 2026-11-10, and 5.7 seconds on an example folder measured by the setup diagnostic on the same day. The timeout of the settings must cover a call queued behind another, so about twice that duration. The command *Diagnose setup* measures the configured command once and recommends that timeout, as the [timeout rule](setup-diagnostic.md#^timeout-rule) of the setup diagnostic states.

## Generated-file freshness

A generated file remains current only while its stored source state matches the state of its source records. The runner provides `ekphrasis_commands.source_state`. First, this checker reads the stored token at a JSON Pointer. Next, it invokes a project command for the current token. Finally, it checks whether the tokens are equal. Therefore, the project command defines and calculates the state.

The checker has three configurable entries:

| Argument | Content |
| --- | --- |
| `command` | Arguments given to the configured interpreter; the command must succeed and write exactly one non-empty line |
| `pointer` | JSON Pointer of the stored source state in the generated instance |
| `root` | Working directory of the command, with the checked file's folder as the default |

The placeholders `{file}` and `{folder}` retain their definitions from a findings command. When the tokens match, the checker adds the context *Source state: current*. When the tokens differ, the checker warns at the configured pointer. The warning instructs the researcher to regenerate the file. If the command fails, then the checker warns at the root. Therefore, an unavailable freshness check cannot appear current.

The configuration is portable across projects. The following example checks Gnomon views stored in a child directory of their source-record folder. Another project sets the schema pattern, command, root and pointer for its own generated files:

```json
{
  "name": "view-freshness",
  "module": "ekphrasis_commands",
  "function": "source_state",
  "schemas": ["gnomon:view.*"],
  "arguments": {
    "command": ["-m", "gnomon", "source-state", "."],
    "root": "{folder}/..",
    "pointer": "/source_state"
  }
}
```

## Execution

The custom checkers run in one Python process, started with the interpreter of the settings when the first checker is needed. The process imports the registered modules, receives each call as a JSON message, and returns the issues as a JSON message, as the decision on [Python checkers](../adr/python-checkers.md) records. The command *Restart Python checkers* stops this process. The next validation starts a new process and imports the modules again. A timed-out call also stops its process, because the same process cannot serve another request while its Python function remains blocked. Three constraints follow for the author of a checker:

- the value, the instance and the returned issues must be representable in JSON;
- a modified module takes effect after the command *Restart Python checkers*;
- a call that exceeds the timeout of the settings is reported as an issue at the declaring field.

A forced stop of the process also stops every process that its pending call started: the command run by the function `findings_log`, and each descendant of that command. Three stops are forced: the stop after a timed-out call, the command *Restart Python checkers*, and the close of a process with a pending call, when the plugin unloads or its settings change. A process without a pending call closes through the end of its standard input instead, so that Python exits normally. The forced stop depends on the platform, with one limitation each:

- On macOS and Linux, the process leads a process group of its own, which the command and its descendants inherit, and the stop kills that group. A descendant that leaves the group, for instance by starting a session of its own, escapes the stop.
- On Windows, the stop terminates every process whose chain of parent processes leads to the checker process. A descendant whose parent process has already exited no longer belongs to that chain, and escapes the stop.

When Obsidian exits without unloading the plugin, no stop runs. The checker process then exits once its pending call returns. ^process-tree-stop

The custom checkers run after the checks computed within the plugin, once the commits pause, so a slow checker delays no edit. Their current issues join the validation report after the built-in issues. When another edit supersedes the source text before a checker returns, the form discards that result.

Custom checkers run on the desktop application of Obsidian only, since they require a Python interpreter. On the mobile application, the form still opens and runs every built-in check, but each custom checker is skipped: the form reports at its declaring field, or at the root for an instance checker, a warning stating that Python checkers run only in the desktop app, and that the file must be opened on a desktop computer to see their findings. On the desktop application without a configured interpreter, the warning names the setting *Python interpreter* to fill.
