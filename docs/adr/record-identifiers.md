# Record identifiers

> [!QUESTION] Goal: how does a link designate a record by its identifier, and how does ekphrasis find that record?

**Amended** on 2026-11-01 by the decision of `geonexus` on [tool roles](https://github.com/esther-poniatowski/geonexus/blob/827474dca64daef110b9d7fe36a4127c2b32b167/docs/_decisions/tool-roles.md): the keyword `x-identifier` belongs to the addressing specification of Anagraphe, and the index of identifiers moves into the TypeScript package of Anagraphe.

The [requirement on field links](../requirements.md#^field-links) admits two ways to designate the record of a field: the path of its file, or the identifier of the record. A link by identifier stays valid after a move or a rename of the file, as the specification of [links](../features/links.md) states. Resolving such a link raises three questions, to be settled before the last step of the milestone *Links*:

1. which component maintains the index that maps each identifier to its file;
2. which syntax a link by identifier takes, given that an identifier is not the path of a file and that Obsidian itself follows the links of a note;
3. how a schema declares which field of a record holds its identifier.

The [evaluation of rules across files](../architecture/implementation-plan.md#^rules-across-files) set aside such an index on 2026-10-19. The milestone *Links* reopens that evaluation for resolving links only.

## Decision

The record recommends three choices. Its status stays `proposed` until the user decides. Spikes must also confirm two premises of the second choice, listed under *Verification*.

1. **Index**: a module of ekphrasis maintains the index of identifiers. Its pure part lies in the domain layer behind a port, so that a separate plugin could take it over if a second consumer appears.
2. **Syntax**: a link by identifier is a URI of Obsidian handled by ekphrasis, such as `obsidian://ekphrasis?id=quest.pendulum.sustained-oscillation&field=task.epistemic_aim`.
3. **Declaration**: the root of a schema names the field path of the identifier by a new keyword of ekphrasis, `x-identifier`, such as `x-identifier: identity.id`.

## Constraints

- **Binding**: the field holding the identifier depends on the record type. Ekphrasis alone binds a file to its schema, by its modeline or by the path rules of the settings, as the decision on [schema binding](schema-binding.md) records.
- **Links in notes**: a link written in a note is followed by Obsidian. Therefore, ekphrasis can reach such a link only through a hook. That hook must be declared by the API of Obsidian, since an undeclared hook can change without notice at each release of Obsidian.
- **No side effect**: following a link must never create or modify a file.
- **Consumer independence**: ekphrasis must read no keyword defined by a single consumer project, since it ignores every keyword prefixed `x-` outside its own, as the [keywords of ekphrasis](../features/schemas.md) state.
- **Consumer identifiers**: the identifiers of both consumer projects must be indexable:
  - in gnomon, every record holds its identifier at the root key `id`, prefixed by its type, such as `quest.TOPIC.NAME` or `system.TOPIC`. A reference names a symbol of another record by the identifier of that record and the symbol, as `system.TOPIC#SYMBOL`;
  - in geonexus, each schema names the key of the identifier for its own checker, under `x-checks.id_key`: `id` in the glossary and notation schemas, and `identity.id` in the project and audience schemas. An identifier is unique among the files of one type only.

## Options weighed

### Location of the index

| Option | Benefit | Cost |
| --- | --- | --- |
| Module of ekphrasis | The index reads the schema bound to each file, through the binding already resolved by ekphrasis; one plugin is installed and versioned | Ekphrasis grows by a module that watches the vault; parsing every YAML file of a large vault at start-up delays the first resolution, unless the index is built lazily |
| Separate plugin exposing an API | The index serves other uses, such as backlinks between records or a check of a whole project, and is released on its own | The API of Obsidian declares no access from one plugin to another, so each call relies on internals of Obsidian or on a global object. The plugin must also reproduce the binding of files to schemas, or depend on ekphrasis for it |
| Metadata cache of Obsidian | Obsidian maintains the cache | The API declares the cache for the contents of notes, such as their frontmatter, headings and links, so the identifiers held by YAML records are absent from it |
| Index generated by each project, such as the vocabulary of gnomon | Reuses the implementations of the projects, as the custom checkers do | Each project writes a different format, and the index is stale between two runs of its generator |

### Syntax of a link by identifier

A wikilink or a Markdown link without a scheme is an internal link: Obsidian resolves its path through the metadata cache, and opens the file reached. An identifier is never the path of a file, so each candidate below needs another route from the click to ekphrasis. Inside a value of a form, ekphrasis renders the links and handles their clicks itself, as the [value renderer](../../src/adapters/obsidian/value-renderer.ts) does for internal links. Therefore, the three candidates differ only for the links written in notes.

| Candidate | Example | Benefit | Cost |
| --- | --- | --- | --- |
| URI of Obsidian handled by ekphrasis | `[aim](obsidian://ekphrasis?id=quest.pendulum.sustained-oscillation&field=task.epistemic_aim)` | The API declares `registerObsidianProtocolHandler`: its handler receives the decoded query. The same link also opens the record from another application | The link is long, and a field path holding brackets or quotes must be percent-encoded. Obsidian omits such links from its suggestions and from its backlinks |
| Custom URI scheme | `[aim](ekphrasis:quest.pendulum.sustained-oscillation#task.epistemic_aim)` | The link is short, and follows the form of the references of gnomon: an identifier, a hash sign, a name | The API declares no route from a link of an unknown scheme to a plugin, so ekphrasis must intercept the click on such a link in the reading view and in the editor, through elements and classes left undeclared by the API |
| Path-like form resolved on failure | `[[quest.pendulum.sustained-oscillation#task.epistemic_aim]]` | The syntax of Obsidian is kept, together with its suggestions | The link stays unresolved, and a click on an unresolved link creates a note of that name. The API declares no hook through which ekphrasis acts before that click creates the note. Obsidian also resolves the link to any note named like the identifier |

### Declaration of the identifier

| Option | Benefit | Cost |
| --- | --- | --- |
| Root keyword `x-identifier` holding a field path | Names `id` for gnomon and `identity.id` for geonexus in the [field-path syntax](../features/field-paths.md) already used by rules and issues; reads no consumer keyword | A geonexus schema names its identifier twice, by `x-checks.id_key` and by `x-identifier`, and the two values can diverge |
| Project keyword `x-checks.id_key` of geonexus | No second declaration in geonexus | Couples ekphrasis to one consumer, against the constraint of consumer independence; gnomon declares no such keyword |
| Flag `x-identifier: true` on the property of the identifier | Declared beside the marked field | The property `identity.id` of geonexus refers to the definition `id` of the glossary schema. That definition also types the keys of the entries of a glossary and the references to them, so a flag on it would mark each of these fields |
| Root key `id` by convention, with an override | Needs no declaration for gnomon | geonexus still needs the override, and a file bound to an unrelated schema with a key `id` enters the index |
| Path rule of the settings | Keeps the schema unchanged | The identifier belongs to the record type, declared by the schema. A schema shared across vaults would also need the same setting in each vault |

## Consequences

- The milestone *Links* adds the keyword `x-identifier` to the [keywords of ekphrasis](../features/schemas.md), and the question and target-system schemas of the gnomon fixtures declare `x-identifier: id`.
- The index is updated whenever a YAML file is created, changed, renamed or deleted. The index maps each identifier to the files declaring it. An identifier declared by several files is ambiguous: a link to it opens no file, and a notice lists the files. The identifiers of geonexus are unique within one type only, so two types can share an identifier.
- The command *Copy link to field* copies a link by identifier when the schema of the instance declares `x-identifier`. Otherwise, it copies a link by path, in the link format of the settings of Obsidian.
- Links by identifier are absent from the backlinks of Obsidian, whereas links by path appear there.
- The rules across files keep running as custom checkers. A predefined checker of references could later read the same index, through a decision of its own.

## Verification

Three facts used under *Options weighed* are settled by the API declarations of `obsidian` 1.13.1 and of `obsidianmd/obsidian-api` at version 1.14.4:

- `Plugin.registerObsidianProtocolHandler(action, handler)` passes to `handler` the action and the decoded key-value pairs of the query, such as `{action: 'open', key: 'value'}` for `obsidian://open?key=value`;
- `MetadataCache.getFirstLinkpathDest(linkpath, sourcePath)` returns `TFile | null`, `TFile` being the type of every file of the vault, and `parseLinktext(linktext)` splits a link into a path and a subpath starting with `#`;
- the API declares no event fired by a click on an unresolved link, and no method of one plugin reaching another.

The two premises of the recommended syntax were confirmed in a test vault on 2026-10-23, by the [protocol of the corrections](../../tests/manual/protocols/corrections-guidance.md):

- a click on a link `obsidian://…`, in the reading view and in the live preview of a note, reaches the handler of the plugin without leaving the vault;
- such a link without the parameter `vault` acts on the open vault. With the parameter, Obsidian consumes `vault` to choose the vault, and the handler receives the other parameters only.

A negative verdict on either premise reopens the choice of syntax before the last step of *Links*.
